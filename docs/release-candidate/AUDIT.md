# Floody 2.0 release-candidate audit

Reviewed November 9, 2026, for the November 11 school presentation. Review scope was the existing web and native implementation. No application changes were made for this audit. See [validation evidence](VALIDATION.md) for commands, scope and results.

## Reviewed implementation

- **Navigation and layout.** Web has a scrollable document, a desktop rail and a mobile bottom bar. Desktop and mobile interaction checks reached the primary controls on guest entry, dashboard, map planner, report and garage. Native uses separate state-driven tabs, safe-area views and keyboard-aware scrolling. Device behavior remains unverified here.
- **Typography and icons.** Web loaded the local Google Sans Flex face in Edge. Expo exported both native bundles with the TTF and all 13 Material Symbols PNGs. Font fallback is implemented on native. Device rendering, tinting and VoiceOver/TalkBack need manual verification. [Expo SDK 58 reference](https://docs.expo.dev/versions/v58.0.0/)
- **Map and route state.** The web adapter validates GeoJSON, flips longitude/latitude for Leaflet, fits bounds and removes the path on edits or failed requests. The route appeared before optional destination weather in the deterministic test. The live OSRM request rendered a 63-point route. Native uses a separate bundled Leaflet WebView bridge. The bridge validates geographic coordinates and renders local report labels as text. Local artifacts verify bundling, while device gestures and permission flows remain open.
- **Weather, alerts and lookup.** Open-Meteo supplies modeled accumulation in mm for the interval ending at the stated validity time. The app formats epochs in America/Recife and rejects missing units/timestamps. An unresolvable location shows an error without triggering Recife weather. INMET alerts, distributed by RadarMeteorológico, remain separate from modeled precipitation and local reports. A live feed response is not evidence of local hazard absence. [Open-Meteo contract](https://open-meteo.com/en/docs)
- **Persistence and catalog.** Browser checks verified a pending report and a saved vehicle through reload. The service tests reject invalid records and client-side approval. The web model result is keyed to the selected make and ignored after a make change. Native catalog requests use a picker identity guard and offer manual entry. Native runtime persistence, permissions and catalog interaction remain device checks.
- **Safety and external failures.** Route results warn that they do not account for flooding or guarantee passage. Weather and alerts distinguish unavailable responses from successful empty data. Confirmed satellite fallback and external provider restrictions are listed above. The audit did not send real addresses, incident descriptions or personal coordinates to live geocoding.

## Follow-up order

1. Before public distribution, review external location disclosure and the open provider requirements in [the provider review](PROVIDERS.md).
2. On iPhone and Android, exercise both themes, fonts and icons, keyboard/safe areas, map gestures, GPS denial and regrant, report and vehicle persistence, and back navigation.
3. Make layer fallback and GPS tracking state explicit, expose pending reports on web, and broaden accessibility and failure-state coverage.
